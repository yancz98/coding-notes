## Collector 部署模式

>   Collector 的部署模式直接影响系统的性能、可靠性和可管理性。

| 部署模型                   | 架构说明                                                     | 适用场景                                                     | 优势                                                         | 挑战                                                         |
| :------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **Agent 模式**             | 每个节点（Kubernetes DaemonSet）运行一个 Collector，负责该节点上所有应用的遥测数据。 | 中小规模集群，希望快速实现节点级的数据处理和丰富。           | 配置简单，能自动丰富节点级别的元数据（如 Pod 信息），数据与节点共存，故障域隔离。 | 配置变更需滚动更新所有 Agent，集中管控能力弱，复杂处理（如尾采样）能力有限。 |
| **Gateway 模式**           | 部署独立、可扩展的 Collector 集群作为中央网关，所有 Agent 将数据转发给 Gateway。 | 大规模集群，需要集中进行数据治理（如多租户隔离）、复杂处理（如尾采样）和跨团队策略管理。 | **集中策略管控**，支持高级处理（尾采样、跨服务关联），解耦数据产生与消费，便于统一路由和成本控制。 | 引入了一层网络开销，Gateway 集群自身成为潜在的瓶颈或单点，需要做好高可用和扩缩容。 |
| **Agent-Gateway 混合模式** | Agent 执行轻量级任务（如丰富元数据、基本采样），Gateway 负责重型任务（如跨集群关联、多后端路由）。 | 超大规模、多集群、多区域部署。                               | 结合两者优点，既能保持 Agent 的轻量，又能实现 Gateway 的集中控制和弹性，扩展性最强。 | 架构最复杂，运维成本最高，需要精细化的监控和调优             |

**性能基准数据**：根据负载测试，对一个处理约 5万请求/秒的 HTTP 服务进行持续追踪，带来的性能开销约为：CPU 使用率提升 35%，内存 RSS 增加 5-8 MB，P99 延迟从 10ms 升至 15ms，网络出口流量增加 4 MB/s。这些数据可作为资源规划和容量估算的起点
